# 03. 예제 실험과 결과 해석

[README](../README.md) · [이전: 코드 분석](02-code-walkthrough.md) · [다음: 테스트](04-testing.md)

아래 값은 저장소에 포함된 입력과 FCFS 계산으로 재현할 수 있습니다.
프로젝트 루트에서 다음처럼 실행합니다.

```powershell
pwsh -File scripts/run.ps1 -Example basic
```

## 실험 1. 기본 입력을 손으로 따라가기

입력: [`basic.txt`](../examples/basic.txt).

| 작업 | 도착 | 실행 | 시작 계산 | 종료 | 대기 | 반환 |
| --- | ---: | ---: | --- | ---: | ---: | ---: |
| P1 | 0 | 5 | max(0, 0) = 0 | 5 | 0 | 5 |
| P2 | 1 | 3 | max(5, 1) = 5 | 8 | 4 | 7 |
| P3 | 2 | 1 | max(8, 2) = 8 | 9 | 6 | 7 |

```text
0 ── P1 ── 5 ── P2 ── 8 ── P3 ── 9
```

평균 대기 = (0 + 4 + 6) / 3 = **3.33**.
평균 반환 = (5 + 7 + 7) / 3 = **6.33**.
P3는 실행 시간이 가장 짧아도 FCFS에서는 먼저 도착한 P2를 앞지를 수 없습니다.

## 실험 2. CPU가 쉬는 구간

입력: [`idle.txt`](../examples/idle.txt). 실행 명령의 `-Example`을 `idle`로 바꿉니다.

| 작업 | 도착 | 실행 | 시작 | 종료 | 대기 | 반환 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| P1 | 3 | 2 | 3 | 5 | 0 | 2 |
| P2 | 8 | 1 | 8 | 9 | 0 | 1 |

```text
[0, 3) IDLE
[3, 5) P1
[5, 8) IDLE
[8, 9) P2
```

평균 대기는 **0.00**, 평균 반환은 **1.50**입니다.
CPU가 쉬었던 시간과 프로세스가 기다린 시간은 다릅니다.
P1은 3에 도착하므로 0~3의 유휴 시간은 P1의 대기 시간에 포함되지 않습니다.

## 실험 3. 뒤섞인 입력과 같은 도착 시간

입력: [`ties-unsorted.txt`](../examples/ties-unsorted.txt).

| 입력 ID | 도착 | 실행 | 실행 순위 | 시작 | 종료 | 대기 | 반환 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| P1 | 5 | 2 | 3 | 5 | 7 | 0 | 2 |
| P2 | 0 | 3 | 1 | 0 | 3 | 0 | 3 |
| P3 | 0 | 2 | 2 | 3 | 5 | 3 | 5 |

실행 순서는 **P2 → P3 → P1**입니다.
P1이 먼저 입력되었어도 늦게 도착했으므로 마지막에 실행됩니다.
P2와 P3는 도착 시간이 같아 먼저 입력한 P2가 우선합니다.
평균 대기는 **1.00**, 평균 반환은 **3.33**입니다.

## 실험 4. 긴 작업이 앞에 있을 때

입력: [`long-first.txt`](../examples/long-first.txt).
모두 시각 0에 도착하며 실행 시간은 입력 순서대로 20, 2, 1입니다.

| 작업 | 실행 | 시작 | 종료 | 대기 | 반환 |
| --- | ---: | ---: | ---: | ---: | ---: |
| P1 | 20 | 0 | 20 | 0 | 20 |
| P2 | 2 | 20 | 22 | 20 | 22 |
| P3 | 1 | 22 | 23 | 22 | 23 |

평균 대기 = 42/3 = **14.00**.
평균 반환 = 65/3 = **21.67**.
1 tick만 필요한 P3도 앞선 작업 때문에 22 tick을 기다립니다.

## 실험 5. 짧은 작업을 먼저 입력하면?

입력: [`short-first.txt`](../examples/short-first.txt).
도착 시간과 실행 시간의 집합은 같지만 입력 순서를 1, 2, 20으로 바꿉니다.
ID는 파일마다 다시 부여되므로 이전 실험의 P1과 이번 실험의 P1은 같은 길이의 작업이 아닙니다.

| 작업 | 실행 | 시작 | 종료 | 대기 | 반환 |
| --- | ---: | ---: | ---: | ---: | ---: |
| P1 | 1 | 0 | 1 | 0 | 1 |
| P2 | 2 | 1 | 3 | 1 | 3 |
| P3 | 20 | 3 | 23 | 3 | 23 |

평균 대기 = 4/3 = **1.33**.
평균 반환 = 27/3 = **9.00**.

| 비교 기준 | 긴 작업 먼저 | 짧은 작업 먼저 |
| --- | ---: | ---: |
| 전체 완료 시각 | 23 | 23 |
| 총 CPU 실행 시간 | 23 | 23 |
| 평균 대기 | 14.00 | 1.33 |
| 평균 반환 | 21.67 | 9.00 |

두 실험 모두 FCFS를 실행했습니다. 두 번째 결과는 입력 순서를 바꾼 결과이며,
프로그램이 스스로 짧은 작업을 선택한 것이 아닙니다.
전체 작업량과 최종 완료 시각이 같아도 개별 작업의 체감 대기는 크게 달라집니다.

## 해석의 범위

짧은 작업들이 긴 작업에 막혀 기다리는 모습은 FCFS의 convoy effect를 이해하는 데 도움이 됩니다.
관련 설명은 [MIT 운영체제 강의 노트](https://people.csail.mit.edu/rinard/teaching/osnotes/h6.html)를 참고할 수 있습니다.
현재 모델에는 I/O 장치와 반복적인 CPU/I/O 실행이 없으므로 실제 시스템에서의
CPU·I/O 장치 이용률 변화까지 재현한 실험은 아닙니다.

또한 이 작은 예제로 특정 알고리즘이 모든 상황에서 더 좋다고 결론 내릴 수 없습니다.
V2에서는 **동일 입력을 FCFS와 비선점 SJF에 각각 제공**하는 비교 기능을 추가했습니다.
[V2 비교 실험과 분석](06-ver2-sjf.md)에서 결과를 확인할 수 있습니다.
