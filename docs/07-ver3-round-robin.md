# 07. ver3 — Round Robin과 시간 할당량 분석

[README](../README.md) · [검증 결과](04-testing.md) · [개발 계획](05-roadmap.md)

이 문서는 V3 학습 기록입니다. V4에서는 전체 실행 기록을 JSON으로 저장할 수 있습니다.
[V4 파일 입출력 분석](08-ver4-file-io.md)을 참고하세요.

## 1. V2에서 달라진 점

V2의 FCFS·SJF는 작업 하나를 선택하면 끝까지 실행했습니다.
V3의 Round Robin(RR)은 최대 시간 할당량만큼 실행하고, 아직 남아 있으면 준비 큐의 뒤로 이동합니다.
같은 프로세스가 여러 번 CPU를 사용하므로 **프로세스별 최종 결과와 실행 구간 기록을 분리**했습니다.

| 항목 | V2 | V3 |
| --- | --- | --- |
| 알고리즘 | FCFS·비선점 SJF | FCFS·SJF·RR |
| 중간 교체 | 없음 | RR은 시간 할당량 종료 시 교체 가능 |
| 준비 상태 | 정렬 또는 후보 탐색 | RR 원형 큐 추가 |
| 실행 기록 | 프로세스당 하나 | RR은 여러 구간의 동적 배열 |
| 통계 | 평균 대기·반환 | 평균 응답 추가 |
| 비교 | 두 방식 | 세 방식, RR의 q 지정 |

단일 CPU, 하나의 CPU burst, I/O 없음, 문맥 교환 비용 0이라는 가정은 같습니다.
실제 운영체제 스케줄러를 변경하거나 CPU 속도를 측정하지 않습니다.

## 2. 준비 큐의 규칙

1. CPU가 비면 큐의 맨 앞 작업을 꺼냅니다.
2. `min(남은 실행 시간, 시간 할당량)`만큼 실행합니다.
3. 실행 구간이 끝난 시각까지 새로 도착한 작업을 도착 순서로 큐에 넣습니다.
4. 현재 작업이 미완료라면 그 뒤에 다시 넣습니다. 완료했다면 다시 넣지 않습니다.
5. 큐가 비면 다음 도착까지 IDLE로 진행합니다.

동시 도착은 입력 순서를 유지합니다. ID의 숫자 크기는 우선순위가 아닙니다.
시각 t에 새로 도착한 작업은 시각 t에 시간 할당량을 다 쓴 현재 작업보다 먼저 삽입합니다.
이미 큐에서 기다리던 작업은 그 앞 순서를 유지합니다.

## 3. 기본 예제를 따라가기

[`rr-basic.txt`](../examples/rr-basic.txt)는 P1=(0, 5), P2=(1, 3), P3=(2, 1)입니다.
시간 할당량 q=2로 실행합니다.

```powershell
pwsh -File scripts/run.ps1 -Algorithm rr -Quantum 2 -Example rr-basic
```

| 구간 | 실행 | 실행 후 남은 시간 | 새 도착·재삽입을 마친 큐 |
| --- | --- | ---: | --- |
| [0, 2) | P1 | 3 | P2, P3, P1 |
| [2, 4) | P2 | 1 | P3, P1, P2 |
| [4, 5) | P3 | 0 | P1, P2 |
| [5, 7) | P1 | 1 | P2, P1 |
| [7, 8) | P2 | 0 | P1 |
| [8, 9) | P1 | 0 | 빈 큐 |

P3는 정확히 시각 2에 도착하므로 첫 구간이 끝난 P1의 재삽입보다 앞에 들어갑니다.
실행 시간이 q보다 짧게 남으면 그만큼만 실행하므로 P3는 [4, 5)입니다.

| 작업 | 최초 시작 | 최종 종료 | 총 대기 | 반환 | 응답 |
| --- | ---: | ---: | ---: | ---: | ---: |
| P1 | 0 | 9 | 4 | 9 | 0 |
| P2 | 2 | 8 | 4 | 7 | 1 |
| P3 | 4 | 5 | 2 | 3 | 2 |

평균 대기 = 10/3 = **3.33**, 평균 반환 = 19/3 = **6.33**, 평균 응답 = 3/3 = **1.00**입니다.

## 4. 대기 시간과 응답 시간의 차이

```text
반환 = 최종 종료 - 도착
총 대기 = 반환 - 필요한 전체 CPU 실행 시간
응답 = 최초 시작 - 도착
```

P1은 바로 실행되어 응답은 0이지만, [2,5)와 [7,8)에 총 4 tick을 기다립니다.
V1/V2의 `최초 시작 - 도착`을 그대로 RR 총 대기에 사용하면 이 재대기를 놓칩니다.
현재 모델에는 I/O와 문맥 교환 비용이 없어 반환 시간에서 실제 CPU 실행 시간을 빼는 식을 사용할 수 있습니다.

RR 결과 표는 **입력 순서**입니다. 마지막 입력이 가장 늦게 끝난다는 보장이 없습니다.
따라서 전체 완료 시각은 마지막 배열 원소가 아닌 모든 완료 시각의 최댓값으로 계산합니다.
기본 예제에서는 마지막 입력 P3가 5에 끝나지만 전체 완료는 P1이 끝나는 9입니다.

## 5. 원형 큐 구현

[`src/scheduler.c`](../src/scheduler.c)의 `ReadyQueue`는 최대 100개의 인덱스를 담습니다.

```c
typedef struct {
    int items[MAX_PROCESSES];
    int head;
    int size;
} ReadyQueue;
```

꺼낼 위치는 `head`, 다음 삽입 위치는 `(head + size) % MAX_PROCESSES`입니다.
꺼낸 뒤에는 `head = (head + 1) % MAX_PROCESSES`로 이동합니다.
원소를 매번 앞으로 복사할 필요 없이 삽입·삭제를 O(1)에 수행합니다.

빈 상태는 `size == 0`, 가득 찬 상태는 `size == MAX_PROCESSES`로 구분합니다.
현재 실행 중인 작업은 큐에서 꺼낸 상태이므로, 새 도착을 넣고 현재 작업을 다시 넣어도
미완료 프로세스 개수인 100개를 초과하지 않습니다.
삽입 함수는 그래도 용량을 검사하며, 내부 순서에 오류가 생기면 실패를 반환합니다.

## 6. 도착 시각과 남은 실행 시간

원본 입력은 바꾸지 않고 입력 위치를 담은 `order[]`를 도착 시간으로 안정 정렬합니다.
`next`는 아직 큐에 넣지 않은 다음 도착을 가리킵니다.
따라서 매 실행 구간마다 모든 원소를 다시 검색하지 않아도 새 도착을 순서대로 추가할 수 있습니다.

`remaining[]`에는 작업별 남은 CPU 시간을 저장합니다.
최초 시작은 -1로 초기화하고 처음 실행할 때만 기록합니다.
작업이 끝나면 완료·반환·총 대기를 계산합니다.
큐가 비었을 때는 다음 도착 시각으로 바로 이동하며 실제 시간만큼 기다리지 않습니다.

## 7. 실행 기록과 메모리 관리

[`scheduler.h`](../src/scheduler.h)의 `ExecutionSlice`는 원본 배열 위치와 구간의 시작·끝을 저장합니다.
`process_index == -1`은 IDLE이며, ID 값과 분리되어 있습니다.
`RoundRobinResult`는 입력 순서의 프로세스 결과와 실행 기록 포인터·개수를 묶습니다.

```c
RoundRobinResult result = {0};
RoundRobinStatus status = simulate_round_robin(input, count, quantum, &result);
if (status == RR_OK) {
    /* result.processes와 result.slices 사용 */
}
free_round_robin(&result);
```

결과를 다시 사용하기 전에도 해제해야 합니다. 입력과 결과 저장 공간은 별개여야 합니다.
아직 해제하지 않은 결과 포인터를 전달하면 잘못된 입력으로 처리합니다.
`free_round_robin`은 해제 후 구조체를 0으로 초기화하므로 해제된 결과를 다시 해제해도 안전합니다.

실행 구간의 수는 `Σ ceil(burst / q)`로 미리 계산할 수 있습니다.
여기에 최대 n개의 IDLE을 더한 크기만큼 `malloc`으로 확보합니다.
할당에 실패하면 `RR_NO_MEMORY`, 입력 오류는 `RR_INVALID_INPUT`, 구간 상한 초과는 `RR_TOO_MANY_SLICES`를 반환합니다.

## 8. 기록 상한과 화면 표시

최대 입력 100개 × 실행 시간 1,000,000에서 q=1이면 실행 구간은 1억 개가 됩니다.
V3에서는 계산량과 메모리를 제한하기 위해 **100,000개 이하의 실행 구간**만 허용합니다.
상한을 넘으면 일부만 계산하지 않고 시작 전에 안내합니다. q를 키우거나 작업량을 줄여 해결할 수 있습니다.
IDLE 구간은 이 실행 구간 상한에 포함하지 않고 별도 공간을 확보합니다.

계산이 허용된 결과도 콘솔 타임라인은 첫 200개 구간까지만 보여줍니다.
출력이 생략되면 메시지로 알리며, 내부 기록과 최종 통계는 전체 실행을 반영합니다.
전체 기록을 파일로 내보내는 기능은 V4 계획에 있습니다.

## 9. 시간 할당량 실험

기본 예제에서 q만 바꿉니다.

| q | 구간 수 | 평균 대기 | 평균 반환 | 평균 응답 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 9 | 2.67 | 5.67 | 0.33 |
| 2 | 6 | 3.33 | 6.33 | 1.00 |
| 10 | 3 | 3.33 | 6.33 | 3.33 |

q가 모든 작업의 실행 시간 이상이면 각 작업을 한 번에 완료해 이 모델의 RR은 FCFS와 같아집니다.
q가 작아지면 작업들이 더 자주 실행 기회를 얻지만 구간 수가 많아집니다.
현재 모델은 문맥 교환 비용이 0이므로 실제 CPU의 최적 시간 할당량을 찾아낸 실험은 아닙니다.

[`rr-response.txt`](../examples/rr-response.txt)는 동시에 도착하는 실행 시간 10, 1, 1의 작업입니다.
FCFS의 짧은 작업들은 첫 긴 작업이 끝날 때까지 기다리지만, RR q=2에서는 먼저 CPU를 사용할 기회를 얻습니다.
평균뿐 아니라 긴 작업의 최종 완료와 짧은 작업의 최초 응답을 함께 살펴보는 예제입니다.

## 10. 복잡도와 검증

프로세스 수 n, 실행 구간 수 s일 때 도착 정렬 O(n²), 큐 처리 O(n+s), 기록 공간 O(n+s)입니다.
프로세스별 배열은 상한 100의 고정 배열이고 실행 기록만 동적 할당합니다.

별도의 tick 단위 참조 모델과 60개 입력의 전체 타임라인·작업별 결과·세 평균을 비교했습니다.
최대 큐 용량, q 경계값, 입력 보존, 할당된 메모리 해제 등은 C 함수 테스트로 확인합니다.
전체 702개 검사의 구성과 검증 한계는 [테스트 문서](04-testing.md)에 있습니다.
