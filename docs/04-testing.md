# 04. 테스트 방법과 검증 범위

[README](../README.md) · [이전: 실험](03-experiments.md) · [다음: 개발 계획](05-roadmap.md)

## 재현 방법

GCC와 PowerShell 7 이상이 설치된 환경에서 프로젝트 루트 기준으로 실행합니다.

```powershell
pwsh -File tests/test_fcfs.ps1
pwsh -File tests/test_ver2.ps1
pwsh -File tests/test_ver3.ps1
pwsh -File tests/test_ver4.ps1
```

[`test_fcfs.ps1`](../tests/test_fcfs.ps1)은 먼저
[`build.ps1`](../scripts/build.ps1)로 현재 소스를 컴파일합니다.
오래된 실행 파일을 그대로 검사하지 않습니다.
`-std=c11 -Wall -Wextra -Wpedantic -Werror`로 경고도 실패로 처리합니다.

## 고정 사례

| 구분 | 확인하는 내용 |
| --- | --- |
| 기본 입력 | 실행 구간 및 평균 대기 3.33 / 반환 6.33 |
| 유휴 구간 | 최초 도착 전과 작업 사이의 IDLE |
| 뒤섞인 입력 | 도착 시간 기준 실행 순서 |
| 동시 도착 | 입력 순서 유지 |
| 단일 작업 | 대기 0, 반환 = 실행 시간 |
| 최대 입력 | 100개, 각 도착·실행 1,000,000에서 누적 계산 |
| 잘못된 숫자 | 범위 밖 값, 음수, 소수, 문자, 정수 오버플로 |
| 긴 줄 | 버퍼를 넘는 입력을 비운 뒤 정상 재입력 |
| 공백 | 빈 줄 거부, 정수 앞뒤 공백 허용 |
| EOF | 미완료 입력에서 종료 코드 1 및 오류 메시지 |
| 작업 길이 순서 | 긴 작업 먼저 / 짧은 작업 먼저의 평균 차이 |

최대 입력에서는 평균 대기 **49,500,000.00**, 평균 반환 **50,500,000.00**을 확인합니다.
대기 시간 합이 32비트 정수 범위를 넘는 상황도 포함됩니다.

## 독립 참조 모델

난수 시드 42로 만든 40개 작업 집합을 추가로 비교합니다.
각 집합은 1~14개 작업, 도착 0~29, 실행 1~7 범위입니다.
동일한 PowerShell/.NET 실행 환경에서는 같은 시드로 재현할 수 있습니다.
다른 .NET 버전에서 난수열 자체가 바뀌더라도 각 입력의 기대값은 그 자리에서 계산합니다.

프로그램은 미리 정렬하고 다음 시각으로 건너뜁니다.
반면 테스트의 참조 모델은 현재 시각에 준비된 작업을 찾아 하나씩 처리하고,
유휴 시간과 실행 시간을 tick 단위로 진행합니다.
두 결과의 ID·도착·실행·시작·종료·대기·반환 필드 전체를 비교합니다.

같은 코드를 그대로 복제해 테스트하는 대신 다른 진행 방식으로 순서와 시간 계산을 확인합니다.
다만 두 구현 모두 같은 FCFS 명세를 따르므로, 잘못된 명세 자체까지 자동으로 발견하는 것은 아닙니다.
이를 보완하기 위해 [손계산 예제](03-experiments.md)도 함께 제시합니다.

## V1 및 FCFS 회귀 확인 결과

- 확인일: 2026-09-07.
- 환경: Windows, GCC 15.2.0, PowerShell 7.6.5.
- 컴파일: 경고 없음, `-Werror` 통과.
- 테스트: **71개 검사 통과**, 이 중 40개는 독립 참조 모델과 작업 집합 전체 비교.
- 다른 작업 폴더에서 스크립트를 호출하는 경로 검증 포함.
- 문서의 저장소 내부 상대 링크와 Git 추적 파일 범위를 별도로 확인.

```text
PASS: 71 checks, including 40 independent reference workloads.
```

71은 테스트 스크립트의 검사 횟수입니다. 71개의 서로 다른 입력 파일이나
모든 가능한 입력 조합을 의미하지 않습니다.

## V2 추가 검증 — 2026-09-08

V1 검사 71개를 V2 실행 파일에 그대로 적용해 통과했습니다.
[test_ver2.ps1](../tests/test_ver2.ps1)은 다음을 추가로 확인합니다.

- FCFS·SJF·비교 옵션, 도움말, 모드 선택 메뉴와 잘못된 옵션/입력 처리.
- 미래 도착 작업 제외, 준비된 작업이 있을 때 불필요하게 기다리지 않음.
- 실행 중 새 작업이 도착해도 선점하지 않음.
- 종료 시각과 같은 시각에 도착한 작업을 다음 선택에 포함.
- 실행 시간 → 도착 시간 → 입력 순서의 동률 규칙.
- 비교 모드의 각 결과가 단독 실행과 동일함, 비교표의 숫자가 실제 결과와 일치함.
- SJF 단일 작업 및 초기·중간 유휴 구간.
- 시드 20260908의 60개 입력을 독립적인 tick 단위 SJF 참조 모델과 비교.

SJF 참조 모델은 실행 중인 작업을 매 tick 유지하고 완료 후에만 새 작업을 선택합니다.
각 입력에서 결과 표 전체와 두 평균을 검사합니다.

[test_scheduler.c](../tests/test_scheduler.c)는 출력 문자열과 별도로 계산 함수에 직접 접근합니다.
원본 입력을 바꾸지 않는지, 실행 순서가 호출 순서의 영향을 받지 않는지,
ID의 숫자 크기와 무관하게 입력 순서를 보존하는지, 최대 누적값과 잘못된 API 입력을 확인합니다.

```text
PASS: 71 checks, including 40 independent reference workloads.
PASS: 37 C scheduler checks.
PASS: 212 ver2 CLI checks, including 60 SJF reference workloads.
```

합계는 **320개 검사**입니다. 이 중 독립 참조 입력 집합은 FCFS 40개와 SJF 60개입니다.
GCC 15.2.0, PowerShell 7.6.5, Windows에서 `-Werror` 빌드와 함께 확인했습니다.
검사 수는 코드 커버리지 백분율이나 모든 입력의 정확성을 보장하는 수치는 아닙니다.

## V3 추가 검증 — 2026-09-08

[test_ver3.ps1](../tests/test_ver3.ps1)과 [test_round_robin.c](../tests/test_round_robin.c)를 추가했습니다.

- 실행 중 도착과 시간 할당량 끝 시각의 도착을 현재 작업 재삽입보다 먼저 반영.
- 동시 도착은 입력 순서, 서로 다른 시각의 도착은 도착 순서.
- 작업이 끝나는 시각과 새 작업의 도착이 같은 경우 불필요한 재삽입 없음.
- 단일 작업의 여러 구간, 최초·중간 IDLE, q=1 및 충분히 큰 q.
- RR 총 대기와 최초 응답을 구분하고, 마지막 입력이 먼저 완료해도 전체 완료 시각을 올바르게 계산.
- 100개 프로세스가 동시에 준비되는 큐 최대 용량과 인덱스 순환.
- 큰 누적 시간, 실행 기록 100,000개 허용과 100,001개 거부.
- 화면 표시 200개 제한 후에도 최종 통계 유지.
- 원본 입력 보존, 실패 코드, 결과 메모리 해제와 재사용.
- 잘못된 시간 할당량, 중복 옵션, 메뉴 재입력, EOF, 옵션 순서.

RR 참조 모델은 시드 202609083으로 60개 입력 집합을 만듭니다.
C 구현은 도착 정렬·원형 큐·구간 단위 진행을 사용하고,
참조 모델은 매 tick 도착을 검사하며 동적 List에 준비 순서를 저장합니다.
각 입력에서 전체 타임라인, 작업별 결과 표, 평균 대기·반환·응답 시간을 비교합니다.

```text
PASS: 71 checks, including 40 independent reference workloads.
PASS: 37 C scheduler checks.
PASS: 212 ver2 CLI checks, including 60 SJF reference workloads.
PASS: 43 Round Robin C checks.
PASS: 339 ver3 CLI checks, including 60 RR reference workloads.
```

총 **702개 검사**이며 참조 모델 입력은 FCFS 40개, SJF 60개, RR 60개입니다.
V2 테스트는 알고리즘 기대값을 유지하고 V3의 메뉴·출력 형식 변경에 맞춰
비교 섹션 경계, 평균 응답 열, 시간 할당량 메뉴 입력만 수정했습니다.
기존의 잘못된 알고리즘 사례 `rr`는 새로 지원되므로 `unknown`으로 바꿨습니다.
기존 320개 검사를 V3에서 다시 실행해 통과했습니다.

테스트는 일반적인 할당 성공과 해제 경로를 확인합니다.
실제 메모리 할당 실패를 강제로 주입하거나 메모리 검사 도구를 사용하지는 않았습니다.

## V4 파일 입출력 검증 — 2026-09-08

[test_ver4.ps1](../tests/test_ver4.ps1)은 실제 실행 파일과 임시 입력·출력 파일로 다음을 검사합니다.

- 세 알고리즘의 CSV 작업 행·요약 행과 JSON 결과의 모든 필드 일치.
- JSON 타임라인의 작업별 실행 합계·최초 시작·최종 종료와 계산 결과 일치.
- JSON 스키마·프로그램 버전, 시간 단위, 시간 할당량, 선택 규칙, 모델 가정 기록.
- 입력 저장 후 다시 실행한 JSON과 원래 JSON의 완전 일치.
- 키보드 입력 저장, LF/CRLF, UTF-8 BOM, 마지막 줄바꿈 생략, 앞뒤 공백.
- 빈 파일·중간 빈 줄·누락·추가 데이터·문자·소수·음수·범위 초과·정수 오버플로·NUL·긴 줄 거부.
- 파일 없음, 잘못된 BOM, 누락·중복 파일 옵션.
- 기존 파일 보존, 입력과 출력의 충돌, 출력끼리의 충돌, 없는 부모 폴더와 디렉터리 경로.
- 묶음 출력 중 한 경로가 실패할 때 이번 호출의 신규 파일 정리.
- 콘솔 표시가 200개에서 생략되어도 JSON에 201개 구간을 모두 저장.
- RR 구간 상한 초과 시 결과 파일을 생성하지 않음.
- 각 알고리즘의 IDLE 기록과 단독 실행 내보내기.
- 최대 100개 입력·누적 시간·평균의 직렬화.
- 공백이 있는 폴더로 실행 스크립트의 입력·CSV·JSON 묶음 저장.

```text
PASS: 176 ver4 file I/O checks.
```

기존 702개 검사도 그대로 통과해 합계는 **878개**입니다.
테스트 파일은 충돌을 피하도록 `build/ver4-files-<고유번호>/` 아래에 생성하고 Git에서 제외합니다.
수치 비교에는 CSV와 JSON의 정밀도를 사용하며, 화면의 소수 두 자리와 문자열 그대로 비교하지 않습니다.

파일 충돌·경로 오류는 실제로 검증했습니다. 디스크 고갈, 장치 장애, 삭제 권한 박탈,
프로그램 강제 종료를 주입하지는 않았으며 여러 파일의 저장이 운영체제 수준에서 원자적이라고 보장하지 않습니다.

## V5 뷰어 검증 — 2026-09-08

[test_viewer.js](../tests/test_viewer.js)는 V5 샘플 JSON의 구조, RR 구간 경계, 누적 실행·남은 시간·상태,
완료 상태, 잘못된 스키마·가정·버전·16MB 초과를 확인합니다.
`node --check`로 브라우저 스크립트 문법을 확인했고, 루프백 서버가 허용한 HTML/JS 파일을 응답하고
알 수 없는 경로에 404를 반환하는 것도 확인했습니다.

```text
PASS: 24 viewer model checks.
```

기존 878개와 합쳐 V5 현재 검증 합계는 **902개**입니다.
뷰어는 브라우저의 파일 선택과 Canvas를 사용하므로 브라우저별 픽셀 회귀,
모바일 보조 기술 조합, 실제 공개 호스팅 배포는 이 버전의 검증 범위가 아닙니다.

## 남은 검증 범위

Linux/macOS 실행과 GUI는 이 버전의 검증 대상이 아닙니다.
정적 분석기나 메모리 검사 도구를 실행했다는 의미도 아닙니다.
V6에서는 현재 알고리즘·파일·뷰어 검증을 유지하고 대규모 입력 성능 실험을 추가할 예정입니다.
